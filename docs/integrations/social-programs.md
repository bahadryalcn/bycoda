# AI campaign programs

Campaign programs extend the existing SocialService. They produce exact campaign variants and enqueue the existing SocialJobs; there is no second publishing queue. The host advertises `social.programs.v2`, and snapshots expose `programsSupported`. The generic `social.request` native/remote envelope carries the new owner operations, so its existing allowlist remains valid. Old hosts do not display the new controls. Old finite publishing plans retain their original behavior.

## Owner workflow

Create an AI campaign in Campaigns, choose its project/accounts, enter public information, select independent text/image providers and set the schedule and generation limits. Project brand voice and verified facts are available without reading project files. Content angles and templates guide generation. Existing campaign media can be reused, and each account can override the campaign media (including a YouTube video). UTM tags are owner-editable. Save starts paused; saving or generating never enables external sending.

Generate the first occurrence and review each account's text. If text approval is configured, image generation waits for that approval. Review images and remaining steps, then explicitly activate the displayed campaign revision. Semi-approved mode requires the first sample of every revision and the plan confirmation; selecting final publication adds review for every occurrence. LinkedIn always requires final publication review. Automatic mode still requires explicit owner activation of the bounded rule. The user can customize text, image, platform adaptation, schedule and final publication checks.

The program screen shows per-account outcomes and platform receipts, generation counts, resolved models, provider transitions and cancellation/pause reasons. Editing exact content clears its approvals. Queued/dispatched variants are immutable. Bulk link editing affects only editable drafts; it never changes queued/successful targets. Exact failed jobs use the existing job retry controls. Ambiguous outcomes stay in review and are not retried automatically.

AI configuration suggestions are draft form data. Account/project identities, model selection and budgets remain owner supplied; suggestions cannot activate a program, change sending permissions or approve content.

## Models and host configuration

Text uses the existing isolated harness text runner. Account policy is resolved before every generation and checked again after generation and before dispatch. A saved platform agent overrides the campaign agent; the campaign agent overrides the global agent. No unavailable text provider is silently substituted. The prompt uses only the campaign brief and selected owner-verified public facts; it does not include social inbox content, transcripts, project files or credentials. Fact identifiers, character limits, unfamiliar links and unsupported numeric/date/version promises are validated, with approximate near-duplicate detection. Model output is not a guarantee of factual correctness or semantic uniqueness; use per-content review when those guarantees matter.

Automatic images try **Codex native ImageGen, Gemini, then local ComfyUI**. The separate paid OpenAI Images API is available only through explicit fixed-provider selection. Every attempted generation consumes a hard generation budget; estimated monetary costs are not fabricated when unavailable. Safety refusals do not trigger another provider.

- Codex runs a separate ephemeral app-server helper with shell and MCP disabled and permission requests declined. Discovery requires an installed runtime exposing an enabled native image-generation feature and an authenticated account. The adapter accepts a returned native image artifact in its isolated directory or the Codex generated-images directory. Only `native-default` is advertised until the runtime exposes independent native image-model selection. Tool presence in a different conversation or a CLI executable alone is insufficient; unsupported runtime protocols remain unavailable.
- Gemini requires host environment `GEMINI_API_KEY` and an explicit `BYCODA_SOCIAL_GEMINI_IMAGE_MODEL`. This is API authentication, independent of a Gemini CLI login.
- The separately billed OpenAI image API requires `OPENAI_API_KEY` and `BYCODA_SOCIAL_OPENAI_IMAGE_MODEL`. It is excluded from automatic fallback.
- ComfyUI requires `BYCODA_SOCIAL_COMFYUI_ENDPOINT`, `BYCODA_SOCIAL_COMFYUI_WORKFLOW` (path to an owner-maintained API workflow JSON), and optionally `BYCODA_SOCIAL_COMFYUI_MODEL` (display/selection identifier). This version accepts only an explicit loopback endpoint on the selected executor host. Use the existing host selector to choose the machine running ComfyUI; there is no implicit cross-machine fallback. The workflow uses literal value placeholders `{{prompt}}`, `{{width}}`, `{{height}}`, and optionally `{{model}}`. Node types must exist on that server. A model placeholder is accepted only for an input whose choices are advertised by that installed node; the owner can select those discovered models. WebSocket events show bounded node progress, while history polling confirms final artifacts. AI cannot supply node definitions or executable workflows. Jobs retain their external prompt ID and poll bounded history for results. Pausing cancels local waiting without globally interrupting unrelated ComfyUI jobs.

Generated PNG/JPEG assets are checked for dimensions and the requested aspect ratio before storage in the existing host media directory. The separately billed OpenAI API adapter currently supports square images only. Meta adapters require a public HTTPS image URL. Configure `BYCODA_SOCIAL_PUBLIC_MEDIA_BASE_URL` to the HTTPS origin which already reaches this executor's host HTTP server. This does not create a tunnel or publish a server. The host exposes only signed `/social/media/<uploadId>` URLs with an eight-day expiration; it does not expose a directory listing or arbitrary files. Images are prepared within a seven-day generation horizon. The renderer can request authenticated image previews. Account and adapter format restrictions remain authoritative; unsupported video, carousel, Reel or Story modes are not advertised.

Store API keys only in the host service environment or existing credential mechanisms. Never put them in campaigns, frontend storage, repository files or prompts. Environment configuration is not proof of a live generation/publishing account. Native ImageGen, Gemini, ComfyUI and each social account need separate live acceptance on the intended executor.

## Schedule and persistence

`social_programs` stores bounded configuration and owner authorization. `social_occurrences` stores one logical post's account targets, exact content, approvals, generation checkpoints and linked SocialJobs. `social_generation_leases` prevents duplicate concurrent claims and records the executor and expiry. These tables are additive; existing SocialService records and queue rows are not converted.

Schedules support intervals, fixed local times and daily/weekly frequency across selected weekdays. IANA timezones are retained; UTC dates are materialized. A DST gap moves to the first valid local minute and a fold produces one occurrence. Preview and execution share schedule functions. Generation buffers at most seven unsettled occurrences within seven days. Posting counts describe logical occurrences; account publications are shown separately. Failures never silently create replacements. Continuous mode is explicit and requires bounded daily publication and generation counts.

New generation runs independently of the publication tick. Active programs are revalidated before queue admission and immediately before external dispatch. Restarted generation is held for review. The existing queue's dispatch markers, account locks, cooldowns and uncertain-result handling remain in force. Missed fixed slots move to a future slot, and overdue interval content respects the previous dispatch interval. Multiple programs use the shared account dispatcher. Pausing preserves queued jobs but suspends their program authority; cancellation cancels future queued work. A send already in progress may still complete.

Session MCP/CLI actions are `programs.list`, `programs.configure` (create paused only), `programs.status`, `programs.generate`, and `programs.preview-schedule`. Owner-only actions include `programs.features`, `programs.suggest`, `programs.activate`, `programs.pause`, `programs.cancel`, `programs.approve`, `programs.edit`, `programs.regenerate`, `programs.reschedule`, `programs.resume-image`, `programs.bulk-edit`, and `programs.media-preview`. Content edits and approval require the current occurrence revision; activation/configuration edits require the current program revision. Status pages return up to 50 occurrences and a `nextBefore` sequence cursor.

Real publication requires the existing external-sending switch, valid project publication grants, account connection/scopes and adapter support. X disallows repeat/pool automation. LinkedIn AI content always receives owner review. YouTube requires a real uploaded video and explicit visibility/audience/synthetic-media declarations. These controls do not bypass platform API access, quota or policy restrictions.

X and YouTube access tokens can refresh when their existing vault credential contains a valid refresh token. Rotation is serialized with credential changes, rechecks account identity before storing, and rejects scope changes. A successful rotation updates expiry without expanding campaign authority. Other integrations or revoked refresh tokens require reconnection. This source behavior has mocked-provider coverage; real OAuth acceptance is separate.
